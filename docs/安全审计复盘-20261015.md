# 我在自己的项目里发现了一个真实的数据暴露问题

> 这不是一篇"我发现了 N 个漏洞"的清单。我想复盘的是另一件事：**我为什么会漏掉它们，以及最后是怎么发现的。**

项目背景：一个大学物理实验排课系统，FastAPI + React + CP-SAT 约束求解，处理真实的 433 条课程安排、17 个班、13 位教师。它有一个公网可访问的演示链接。

2026 年 10 月 15 日，我做了一次针对线上服务的安全审计，随后持续到 10 月 24 日。共 24 轮修订，发现了 6 个 P0、若干 P1/P2。下面挑几个真正值得讲的。

---

## 一、最严重的问题：整个 API 完全没有鉴权

加固前的状态：线上 `/api/reschedule/**` **完全没有鉴权**。写接口（清空工单、审批、替换排课表）和真实学生身份接口，对匿名访客全部开放。

`GET /student-status` 匿名请求返回 200，里面是真实学生姓名、学号和 27 门课。

**根因不是某个函数写错了，而是"根本没有这层东西"：**

```python
# main.py:45
app.include_router(reschedule.router)   # 没有 dependencies=
# reschedule.py
router = APIRouter()                     # 没有依赖
# 全文件 grep -c "Depends(" 结果 = 0
```

这不是"忘了加"，是**当时压根没有鉴权这个概念**——因为是我一个人开发、一个人演示，从头到尾都是管理员视角，从没想过"匿名访客"这个角色。

## 二、第二个根因更隐蔽：`.gitignore` 保护不了线上

仓库里有真实排课表 `schedule.xlsx`，其中"教师联系表"带 17 个真实手机号。我已经把它写进 `.gitignore`——在 git 里它是安全的。

但发布平台的上传器**只排除 `node_modules` / `.git` / 构建产物，不读 `.gitignore`**。于是这份文件照样被传到了线上环境。

这里有个值得记住的认知错位：**`.gitignore` 是版本控制的边界，不是部署的边界。** 我以为"没进 git 就不会泄露"，但这两个通道是独立的。

修复分两层：

- 解析层只取姓名和备注，联系方式列在进入系统前就被剥离，由 `test_privacy_export.py` 三层锁死（解析层 / API 层 / 真实数据层原样回归）
- 发布预检 `preflight_release.py` 加了一道：检测到真实表在仓库根就直接拦截发布

## 三、一个真正的 RLS 绕过：`TRUNCATE`

这是我学到的最深的一条 PostgreSQL 知识。

我用了云数据库的行级安全（RLS）来保护工单表，配好策略后觉得稳了。但复查权限时发现，平台给新建表**自动**授予了 `TRUNCATE / TRIGGER / REFERENCES` 给 `authenticated` 和 `anon` 角色。

问题是：**PostgreSQL 的 RLS 对 `TRUNCATE` 完全不生效**——因为 `TRUNCATE` 不是行级操作，它清空整张表，根本不走行级策略判断。

也就是说：我把 RLS 策略配得再严，任何一个登录用户都能一条 `TRUNCATE` 清空整张工单表。**RLS 是边界，但 `TRUNCATE` 从边界旁边绕过去了。**

修复用定向最小权限，不是 `REVOKE ALL`：

```sql
revoke truncate, trigger, references
  on reschedule_requests, consult_logs, app_admins
  from authenticated, anon;
```

这条的教训写在文档里："不要假设『新建表 = 最小权限』。平台会自动授予一整套默认权限，RLS 策略是真正的边界，而 `TRUNCATE` 这类非行级权限必须显式 `REVOKE`。"

## 四、限流加了，线上却完全没生效

这是排查过程中最曲折的一个。

后端原先零限流（`grep limit|rate_limit|throttle|slowapi` 全库 0 命中），`/chat`（消耗 LLM 额度）、`/admin-login`（可爆破口令）都无闸。我加了一个滑动窗口限流，本地压测第 31 次稳定返回 429。

**上线后线上压测：34 次全是 401（鉴权拦截），一次 429 都没有。**

排查结论：边缘网关**覆盖**了客户端的 `X-Forwarded-For` / `X-Real-IP`，且注入的源 IP **逐次变化**。我的"单 IP 计数桶"在线上永远攒不满——每个请求看起来都来自一个全新的 IP。

解法是给限流加一个**客户端指纹维度**（User-Agent + Accept-Language 的短哈希），与源 IP、全站桶三个维度任一超限即 429。加完之后，线上同 UA + 轮换 IP 的压测第 31 次稳定 429，`Retry-After: 56`。

这条的启示是：**"单 IP 限流"这个常见做法，在一个 IP 无法信任的部署环境里是失效的。** 我在本地永远测不出来，因为本地没有那层网关。

## 五、写路径的一个 P0：审批通过，数据却没落地

前几轮审计都在验"读"路径——数据能不能被匿名读到。直到某一轮我才意识到：**从没验过"写"路径。**

结果抓到一个 P0：教秘在界面上点"同意"，页面显示审批成功，但**排课数据根本没有变动**。

原因：

```ts
// App.tsx:766  handleApprove
// 只把云表的 status 改成了 approved
// 而真正能移动记录、检冲突、持久化重放的 _apply_reschedule
//   只挂在 POST /requests/{id}/approve 上
// 前端对这个接口的调用次数 = 0
```

所有界面（沙盘、我的课程、数据体检）都看不见这次调课，但页面说成功了。

修复：新增 `POST /api/reschedule/apply-move`（挂 `require_admin`，不碰工单表，只按调课内容移动记录），加 `applied_moves.idem_key` 幂等列（审批按钮没有 `disabled`，双击会打两次），前端对三种结局分别提示。新增探针 `probe_approval_chain.py`（11 项，修复前只过 6 项）。

## 六、一个"假绿"：看起来有测试在守，其实一次都没守过

这是关于**测试本身**的问题，我认为比前面任何一个都值得反思。

我写了一个 UI 探针去守"数据看板"这个功能。它在 CI 里一直 PASS，前几轮的"无回归"结论都依赖它。

然后我做了一次**证伪性实测**：故意用 `route.abort()` 把 data-audit 接口打断，看探针会不会红。

**它照样 PASS。**

根因：探针的等待条件和最终断言匹配的是 `/数据体检|冲突|统计/`，而这个词出现在视图的**静态副标题**里——"…教室/教师冲突扫描"。接口挂了，副标题照样渲染，断言照样命中。

也就是说：**这个探针从写下那天起，一次都没有守过任何东西。** 前七批的"无回归"结论里，这一项是无效票。

修法是只认"数据到达之后才会出现的字符串"（`共 N 条安排`、`N 间场地`、`平均教室利用率`），并加一条反断言"不得出现失败卡"。修完再跑同样的反证：探针从 PASS 变成 FAIL，界面出现"体检没能完成"失败卡——这才是它该有的行为。

## 复盘：四个反直觉的教训

**1. 我的前十轮审计全在验界面，从没人验过产品对用户的核心承诺。**

这个产品对教秘的唯一承诺是"推荐的时段不撞课"。前十批测试都在验界面渲染、接口返回，**没有任何一个在验这条承诺**。直到我新写了一个 `audit_conflicts.py`——**不复用后端解析器**，直接读原始 Excel、用真实时钟区间判重叠——才抓到：教师占用约束写在循环外，只禁了最后一间教室，真实表里有 **7 个班共 48 处**把同一位老师排在同一时段的两个班，而接口的说明文字写着"教师三重互斥"。

**2. 主动去试会不会被绕过，和被动等它出错，是完全不同的两件事。**

上面所有真实问题（探针假绿、RLS 绕过、非管理员越权审批、限流失效）都是**主动证伪**才发现的。如果只靠"跑一遍测试看绿不绿"，它们会一直绿下去。最有价值的那一刻往往是"我预期它会红，它真的红了"——以及"我预期它会红，它居然绿了"这种时候。

**3. 验证路径必须与被修路径不同，否则是自证。**

我曾修过一个偶发失败，验证方式是"跑满载验收 10/10 × 2 次"——但走的正是被我改掉的那个入口。绿了，我以为修好了。下一轮全量回归，同一个问题又红。**用同一个入口验证自己的修复，永远看不到另一个入口没修。** 这类错我犯了不止一次。

**4. "看起来有测试在跑"不等于"测试在守东西"。**

一个断言吃静态文案的测试、一个只在特定初始状态下才能跑的检查，它们产出的绿色是**没有信息量的**。判断一个检查有没有用，不看它写成什么样，而看**在真实执行环境里它是否真的执行了、真的会在该红的时候红**。

## 修完之后

加固结果（关键几项，均在线上实测验证）：

| 项 | 加固前 | 加固后 |
|---|---|---|
| 学生数据接口 | 匿名 200，含真实姓名/学号 | **401**；管理员令牌 200 |
| 写接口（清空/审批/上传） | 匿名可调 | 全部 **401** |
| 口令 | bundle 里明文 + UI 公示 | bundle **0 命中**，改服务端校验 + 会话令牌 |
| 上传路径穿越 | 可写回仓库根 | 三种写法全压在数据目录内 |
| 云表 TRUNCATE | authenticated/anon 均持有 | 已定向撤销 |
| 审批权限 | 任何登录用户 | 仅 `app_admins` 表内 uid（非管理员 0 行 / 管理员 1 行） |

工程侧：后端测试从审计前的 98 条增长到 850+ 条，新增 23 个独立审计/探针脚本——其中冲突校验器**不复用后端解析器**，从原始 Excel 独立重算，避免"用被测代码验证被测代码"。

一个有意识的取舍：教学秘书演示主路径上的几个只读接口（`/status`、`/teachers`、`/chat`、`/data-audit` 等）**保留免鉴权**，靠限流兜资源滥用。理由是这些数据不含 PII（无联系方式、无学生个体数据），而演示链接需要零门槛打开——完全锁死会让产品失去演示能力。这是一个显式的风险接受决策，不是遗漏。
