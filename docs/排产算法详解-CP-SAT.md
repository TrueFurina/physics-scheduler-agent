# 排产算法详解：用 CP-SAT 求解物理实验排课

> 这份文档讲清楚排课的数学建模：决策变量是什么、约束怎么表达、目标函数为什么长这样。这是整个系统最核心的部分。

## 1. 问题本质

物理实验排课是一个**约束满足 + 优化**问题：把一批「实验项目 × 学生组别」的教学单元，安排到「周次 × 星期 × 时段 × 教室」的网格里，要求互不冲突、且尽量均匀摊开。

它难在**四类资源互相牵制**：一间教室同一时段只能给一个组、一位教师同一时段只能在一个地方、一个学生组同一时段只能上一次课。任何一个约束漏掉，教秘拿到的就是一份看起来排好了、实际会撞车的表。

选 **OR-Tools CP-SAT** 而非手写贪心或回溯，是因为冲突本质是约束传播问题：贪心会陷入局部最优（先排的占了好格子，后排的无处可去），而 CP-SAT 能在一次求解里同时看到全部约束。

## 2. 两个求解器，两种场景

系统里有两个独立的 CP-SAT 建模，对应两种真实场景：

| | 全排课（`auto_scheduler`） | 并行批量排课（`parallel_scheduler`） |
|---|---|---|
| 场景 | 教秘上传新教学大纲，从零排全校 | 一个班一学期「全部实验 × 全部组别」一次排定 |
| 粒度 | 单个教学任务（project × group） | 教学单元，含「实验项目 × 学生组」 |
| 资源维度 | 周次 × 星期 × 时段（教室按并发上限建模） | 周次 × 时段 × 教室（固定星期） |
| 优化目标 | 两阶段：先数量、再摊平 | 单阶段：尽早完成 |
| 典型规模 | 全校 171 个任务 | 单班约 10–18 个单元 |

下面分别讲。

---

## 3. 全排课：两阶段优化

### 3.1 决策变量

对每个教学任务 `i`，在它的**可行域**内为每个格子建一个布尔变量：

```python
x[(i, w, d, t)] = model.NewBoolVar(f"x_{i}_{w}_{d}_{t}")
# i=任务, w=周次, d=星期, t=时段
```

关键在**可行域的预剪枝**：不是为所有 (周, 星期, 时段) 组合都建变量，而是先算出每个格子有哪些教室空闲、哪位教师被占、哪间教室被其他课占用，只给真正可行的格子建变量。这一步把搜索空间砍掉了大半。

### 3.2 三类约束

**① 每个任务最多排一次**（一个任务不必非排不可，所以是 `≤ 1` 而非 `== 1`）：

```python
for i in range(len(sections)):
    vs = [x[(i,) + cell] for cell in domains[i]]
    if vs:
        model.Add(sum(vs) <= 1)
```

**② 教室并发上限**：同一 (周, 星期, 时段) 格子里，同时上课的任务数不能超过该格空闲教室数：

```python
for cell, vs in cell_groups.items():
    cap = len(free_rooms[cell])
    if len(vs) > cap:
        model.Add(sum(vs) <= cap)
```

注意这里没有把「哪个任务进哪间教室」建成变量——因为教室本身不是稀缺维度（只要数量够），稀缺的是**教师和学生组**。把教室退化成并发上限，变量数从 `O(任务 × 格子 × 教室)` 降到 `O(任务 × 格子)`，规模小一个量级。

**③ 教师 / 班级互斥**（同一周、同一星期、同一时段，只能有一个任务）：

```python
for groups in (teacher_groups, class_groups):
    for vs in groups.values():
        if len(vs) > 1:
            model.Add(sum(vs) <= 1)
```

### 3.3 目标函数：为什么要分两步

这是全排课最值得讲的设计。

**第一步：最大化排入数量。**

```python
model.Maximize(sum(x.values()))
```

这一步求出「最多能排进去 K 个任务」。但只做这一步有个坏毛病——**CP-SAT 会把 K 个任务全塞进前几周**。我实测过：30 个任务，求解器给出「第 1 周 12 个、后面几周空着」。数量没错，但这不是一份能交给教秘的学期初稿——真实的排课表每周 27–69 条，是**摊开**的。

**第二步：固定数量 K，最小化「单周任务数」的上界。**

```python
model.Add(sum(x.values()) == total_placed)   # 锁死第一步的数量 K
z = model.NewIntVar(0, total_placed, "max_week_load")
for w in weeks:
    in_week = [v for (i, ww, d, t), v in x.items() if ww == w]
    if in_week:
        model.Add(z >= sum(in_week))         # z 是「最重那一周」的任务数
model.Minimize(z)                            # 让最重的那周尽量轻
```

这是经典的 **min-max**：不要求每周任务数一样多（那可能无解），只要求**最重的那一周尽量轻**。锁死 K 之后，求解器不能再靠「少排几个」来偷懒，只能老老实实把任务往空闲的周次匀。

第二步如果超时或失败，**退回第一步的解**——宁可拿到一份「数量够但没摊平」的表，也不返回失败。排课是帮教秘省事的工具，一份能用的初稿远胜于一个报错。

### 3.4 为什么全校一键必须分片

全校 171 个任务不是一次建模的。实测证据：171 个任务一次性建模（16 周 × 15 时段 + 摊平目标），**6 秒时限内连可行解都拿不到**（`status=UNKNOWN`）；而 60 个一片，7 秒内可解。

于是采用分片：每 60 个任务一片，逐片求解。但分片之间**不是独立的**——前一片排定的 (周, 星期, 时段) 上的教室 / 教师 / 班级占用，必须**回填**成后一片的约束，否则两片会互相「看不见」而把同一格重排给两个任务。回填逻辑在预剪枝阶段完成（见 3.1 的 `class_busy`）。

这里有个更能说明工程态度的细节——**求解时限是怎么定的**。摊平那一阶段曾设为 5 秒（一阶段共 7 秒），比「7 秒可解」的实测点还紧 2 秒。真实表的**第 2 片**（带着第 1 片回填的占用，可行域更小、约束更紧）在 5 秒边界上时灵时不灵：单独跑 5 次里 4 次 `UNKNOWN`。后果是教秘点一次「全校初稿」，有 4/5 的概率只拿到 111/171 的部分结果。

关键判断：**这不是求解器退化，是时限给错了。** 把一阶段时限从 5 秒放宽到实测验证过的 7 秒后，问题消失。

这个例子值得单独记住：**性能问题先问「时限/阈值是不是设错了」，再怀疑算法。** 我的本能反应是怀疑求解器不行了、或者分片策略要重设计——但真正的根因是一个参数比实测可行点紧了 2 秒。调参不是玄学，是照着实测数据设。

## 4. 并行批量排课：四类互斥约束

这个求解器解决的是「一个班一学期全部实验」的编排。它的教室是显式变量（`x[(i, w, t, r)]`），因此互斥约束要覆盖得更细。

### 4.1 决策变量

```python
x[(i, w, t, r)] = model.NewBoolVar(...)
# i=教学单元, w=周次, t=时段, r=教室
```

### 4.2 约束 ①：每个单元恰好一次

```python
for i in range(n_u):
    model.Add(sum(x[(i, w, t, r)] for w in range(n_w)
                  for t in range(n_t) for r in range(n_r)) == 1)
```

和全排课不同，这里是 `== 1`——大纲里的每个「项目 × 组别」单元都**必须**排上，一个都不能少。

### 4.3 约束 ②：同组同周最多一个实验

```python
for _g, idxs in group_units.items():
    if len(idxs) > 1:
        for w in range(n_w):
            model.Add(sum(x[(i, w, t, r)] for i in idxs
                          for t in range(n_t) for r in range(n_r)) <= 1)
```

这是**真实教学节奏的建模**：一个学生组一学期有十来个实验要做，但每周只来一次实验室，所以同组在一周内最多做一个实验。少了这条，求解器会把所有实验堆进前两周——技术上合法，教学上不可行。

### 4.4 约束 ③：场地 / 同组 / 同教师 三重时段互斥

对每个 (周, 时段)：

```python
for r in range(n_r):
    # 场地互斥：一间教室同一时段只能给一个单元
    model.Add(sum(x[(i, w, t, r)] for i in range(n_u)) <= 1)
for _g, idxs in group_units.items():
    # 同组互斥：一个组同一时段只能在一个教室
    if len(idxs) > 1:
        model.Add(sum(x[(i, w, t, r)] for i in idxs for r in range(n_r)) <= 1)
for _te, idxs in teacher_units.items():
    # 同教师互斥：一位教师同一时段只能在一个教室
    model.Add(sum(x[(i, w, t, r)] for i in idxs for r in range(n_r)) <= 1)
```

注意同教师互斥的写法：**对每个时段遍历每间教室求和**，覆盖全部教室。这不是随手写的——它曾经是本系统最严重的一个 bug，见第 5 节。

### 4.5 约束 ④：外部占用的禁用

排课表不是从零开始，有些教师和教室在其他课程里已经有安排。这些时段必须**逐个教室禁用**：

```python
for i in range(n_u):
    te = unit_teacher.get((u["project"], u["group"]))
    teacher_busy_here = bool(te) and (wk, ts, te) in teacher_occupied
    for r in range(n_r):
        if (wk, ts, rooms[r]) in room_occupied:
            model.Add(x[(i, w, t, r)] == 0)      # 教室被占
        if teacher_busy_here:
            model.Add(x[(i, w, t, r)] == 0)      # 教师被占
```

### 4.6 目标：尽早完成

```python
model.Maximize(sum((n_w - w) * x[(i, w, t, r)]
                   for i in range(n_u) for w in range(n_w)
                   for t in range(n_t) for r in range(n_r)))
```

权重 `(n_w - w)` 让排在前面的周次得分更高——同样的排入数量，求解器会倾向**尽早完成**而不是拖到学期末。这符合教学实际：实验课越早排完，期末越从容。

### 4.7 滚动窗口求解

求解器不是一次性开一整个学期的搜索空间，而是**由小到大尝试窗口**：

```python
windows = sorted({
    min(max(weeks, 1), max_avail),       # 最小可行窗口
    min(max(need_weeks, weeks), max_avail),  # 按需求放宽
    max_avail,                            # 整学期兜底
})
for attempt_weeks in windows:
    ...  # 在这个窗口内建模求解
```

窗口只影响「最多能排到第几周」，不影响排入总数。先试小窗口能在几毫秒内出解，只有真排不下时才放宽到整学期。这是在「求解速度」和「可行性」之间取平衡。

## 5. 一个真实 bug：约束写错一个缩进

并行排课的教师互斥约束，最初写在 `for r` 循环**之外**：

```python
# 错误版本
for w in range(n_w):
    for t in range(n_t):
        for i in ...:
            teacher_busy_here = (wk, ts, te) in teacher_occupied
        # ↓ 这句在 for r 之外，r 停在最后一次循环的值 n_r-1
        if teacher_busy_here:
            model.Add(x[(i, w, t, r)] == 0)
```

后果：`r` 变量停在最后一次循环的值（最后一间教室），于是「教师忙」这个约束**只禁用了最后一间教室**，其余 9 间对这位教师仍然开放。教师互斥实际只覆盖了 1/10 的教室。

**实测后果**：真实排课表里有 **7 个班共 48 处**把同一位教师排在同一时段的两个班——而接口的说明文字还写着「教师三重互斥」。这是一个典型的「约束看起来写了、实际没生效」的 bug，用户完全无法从界面上看出来。

它被发现的路径也值得说：我写了一个 `audit_conflicts.py`，**不复用后端解析器**，直接读原始 Excel、用真实时钟区间判重叠——因为前十几轮测试都在验界面，从没人验过「推荐的时段是否真的不撞课」这条产品对用户的根本承诺。

修法就是把那两行移进 `for r` 循环内。校验器重新跑：48 处教师双排 → **0**。

**教训**：约束建模的 bug 不像界面 bug 那样肉眼可见。一个写错缩进的约束，求解器照样给出「OPTIMAL」状态和一份漂亮的结果——它只是把你没表达对的那部分约束忽略了。**对约束求解器，你必须独立验证它真的遵守了你以为它遵守的约束。**

## 6. 性能工程

### 6.1 Worker 数上限

求解器的 worker 数不是越多越好：

```python
solver.parameters.num_search_workers = min(8, os.cpu_count())
```

每个 worker 会**复制一份模型**，内存随 worker 线性增长。OR-Tools 内存不足时抛的是 `MemoryError: bad allocation`——直接 abort 进程，Python 层拦不住。而且 8 个 worker 在 CP-SAT 上已接近收益平台期，再往上「更多 worker 换更少内存」不划算。所以上限是硬保护，不是调优建议。

### 6.2 CP-SAT 预热

首次真实求解有一次初始化开销（加载求解器、JIT 编译）。系统在后台启动时跑一个两变量的 dummy 模型预热（`engine/warmup.py`，daemon 线程，不阻塞启动），把这次开销挪到启动阶段。**A/B 同机实测：首次 `/parallel/solve` 2.05s → 0.89s（−56%）**，预热本身耗时 448–459ms，状态写入 `/health.solver` 可核对。

### 6.3 时间上限与降级

每次求解都有 `max_time_seconds` 上限，超时后返回当前最优解（`FEASIBLE` 而非 `OPTIMAL`）。排课不需要理论最优——教秘要的是一份能用的初稿，她可以在此基础上微调。所以「够好的解」比「最优解」更有价值。

## 7. 验证策略

约束求解器最大的风险是：**它给出 OPTIMAL，但你建模错了，它就优化了一个错误的模型。** 针对这个，验证分三层：

1. **独立冲突审计器**（`scripts/audit_conflicts.py`）——不复用后端解析器，直接读原始 Excel、用真实时钟区间重算所有重叠，交叉核对求解结果。它抓到了第 5 节那个 48 处的 bug。
2. **灰箱验证**（`scripts/verify_graybox.py`）——检验「缺信息自动补全」时，每一条假设（补了哪位教师、哪间教室）都被逐条报告给用户，不静默猜测。
3. **方案落地探针**（`scripts/probe_land_plan.py`）——检验一键排课的方案「采纳」后真的写回了安排表，而不是只在前端显示成功。
