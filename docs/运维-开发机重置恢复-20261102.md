# 开发机重置后的恢复步骤

> 背景：本项目的开发与三轮自动化迭代跑在一台**学校实验室的机器**上。
> 该机器**关机后系统重置、`D:\github` 整个目录会被清空**。
> 所以「哪些东西在 GitHub 上、怎么恢复」必须先写下来 —— 否则重置之后这份说明自己也没了。

这份文件放在**公开**仓库里，就是为了重置后哪怕什么都记不住，也能从代码仓库找到恢复路径。

---

## 一、两处存放位置

| 内容 | 位置 | 可见性 |
|---|---|---|
| 代码（`backend/` + `frontend/` + 本 `docs/`） | `TrueFurina/physics-scheduler-agent` | 公开 |
| 轮次日志、核验台账、单轮验证报告、工作记忆、一次性工具脚本 | `TrueFurina/physics-scheduler-notes` 的 `notes/` 目录 | **私有** |

笔记单独放私有仓库的原因：其中包含线上暴露面分析、账号排查记录等内部资料，
不适合进公开仓库。两边**分工固定**，不要互相搬。

## 二、恢复（新机器，四步）

### 第 0 步：先补 token

机器重置后，用户环境变量 `GITHUB_TOKEN` 也一起没了 —— 这是**最容易被忘的一步**，
推送脚本读的就是它（脚本里不存任何凭据）。

GitHub → Settings → Developer settings → Personal access tokens，
重新生成一个带 `repo` scope 的 token（要读私有仓库就必须有 `repo`）：

```powershell
# 仅当前会话
$env:GITHUB_TOKEN = "ghp_xxx"

# 长期生效（需重开终端）
[Environment]::SetEnvironmentVariable("GITHUB_TOKEN", "ghp_xxx", "User")
```

### 第 1 步：代码

```powershell
Set-Location D:\github
git clone https://github.com/TrueFurina/physics-scheduler-agent.git work-repo
```

仓库根就是 `backend/` + `frontend/` + `docs/`，clone 到 `work-repo` 目录即与原有布局一致。

### 第 2 步：笔记

```powershell
git clone https://github.com/TrueFurina/physics-scheduler-notes.git D:\github\_notes_restore
```

### 第 3 步：把 `notes\` 铺回 `D:\github`

```powershell
robocopy D:\github\_notes_restore\notes D:\github /E /XC /XN /XO
Remove-Item -LiteralPath D:\github\_notes_restore -Recurse -Force
```

`robocopy` 保留相对路径（含隐藏目录 `.workbuddy\memory\`）。
`/XC /XN /XO` 三个排除开关的作用是：**不覆盖本机已存在且更新过的文件** ——
恢复到一台已经有部分文件的机器上时，不会用旧备份盖掉新东西。
若要从头严格对齐远端，改用 `/MIR`（会删除本地多出的文件，慎用）。

## 三、恢复后自检三条

1. **`ROUND_LOG.md` 末尾有一行指针指向 `ROUND_LOG_续2.md`** —— 两个文件必须都在。
   主文件已超 11800 行阈值，第二期的记录全在续篇，只恢复主文件会漏掉最重要的成果。
2. **`核验台账.md` 第五部分「当前基线」**：`pytest 758/32/0`、前端 `21 文件 / 156 全绿`、
   变异 `56/56`、ruff 0（含 `--unsafe-fixes` 0）、`App.tsx` 1492 行。
   这是判断环境是否正常的唯一口径 —— 跑不出这组数字，先查环境再谈改代码。
3. **`.workbuddy/memory/MEMORY.md` 与每日日志回到 `D:\github\.workbuddy\memory\`**
   —— 注意这是隐藏目录，且在 `D:\github` 下、不在 `work-repo` 下。

## 四、工具链不在仓库里，需要另装

| 项 | 说明 |
|---|---|
| Python | **3.12.x**，原机器装在 `D:\github\py312\`。**不要用裸 `python`**：3.13 没有 `ortools`，`pytest` 也未必对得上 |
| 后端依赖 | `work-repo/backend/requirements*.txt`；`ortools` 锁定版本见 `docs/ortools-compat.md` |
| 前端 | `cd work-repo/frontend && npm ci`，测试用 `npx vitest run --no-file-parallelism`（串行，避免沙箱下模块缓存 `EPERM` 导致随机漏跑文件） |
| 全量后端测试 | `cd work-repo/backend` 并设 `OPENBLAS_NUM_THREADS=1`，约 100 秒 |

## 五、每轮结束怎么备份笔记

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
$md    = @(Get-ChildItem "D:\github\*.md" | % FullName)
$mem   = @(Get-ChildItem "D:\github\.workbuddy\memory\*.md" | % FullName)
$tools = @(Get-ChildItem "D:\github\_*.py","D:\github\*.ps1" | % FullName)
$all   = @($md) + @($mem) + @($tools)
& D:\github\gh_push_tree.ps1 -Repo TrueFurina/physics-scheduler-notes `
    -Message "notes: <轮次>" -DestPrefix "notes" -Files $all
```

约 246 个文件；单次调用超时可拆 `$all[0..81]` / `[82..163]` / `[164..]` 三批。
`gh_push_tree.ps1` 走 Git Data API（本机 git 协议不通），保留相对路径，一次 commit 推完。

**校验口径**：推完必须**逐文件比对 git blob sha**
（`sha1("blob {len}\0" + 文件字节)`，与 `git/trees/main?recursive=1` 里 `notes/*` 的 `sha` 对照），
不能只看「推送成功」。2026-11-02 实测：**246 / 246 identical，0 mismatch，0 missing**。

## 六、为什么文档也要进仓库

本项目的第二轮迭代里，代码每轮都推了，**文档一直只在本地** ——
`ROUND_LOG`、`核验台账`、九份单轮验证报告，一个都没进 GitHub。
这台机器一关就全没了。

教训写在这里：**「推了代码」不等于「备份了项目」**。
凡是恢复后重建不了的东西（判断依据、踩过的坑、仪器事故的口径），都必须离开这台机器。
