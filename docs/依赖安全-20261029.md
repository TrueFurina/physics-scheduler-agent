# 依赖安全记录（2026-10-29）

本文件记录已处理的依赖风险与实测依据，供后续升级时对照。

---

## 1. python-multipart：0.0.20 → 0.0.32

### 为什么必须升级

`0.0.20` 存在**无界 part 头 DoS**（`GHSA-pp6c-gr5w-3c5g`），且**计算发生在鉴权之前**。

### 实测数据

环境：Windows amd64 / Python 3.12.6 / uvicorn 单进程
方法：裸 socket 构造请求，不经任何代理

| 攻击输入 | 0.0.20 | 0.0.32 | 改善 |
|---|---:|---:|---:|
| 1,000 个 part 头 | 5 ms | 2 ms | 2.5× |
| 5,000 个 | 18 ms | 1 ms | 18× |
| 20,000 个 | 73 ms | 1 ms | 73× |
| **50,000 个** | **197 ms** | **1 ms** | **197×** |
| **单个 header 10 MB** | **1,532 ms** | **2 ms** | **766×** |

### 为什么「鉴权之前」是关键的

FastAPI 的 `Depends(require_admin)` 在 **Form/File 解析之后**才执行。
所以即使上传端点全部需要管理员令牌，攻击者**仍可用匿名请求**让服务端消耗 CPU：

```
POST /api/reschedule/upload   （无 Authorization 头）
  → 解析整个 multipart（耗时在此）
  → 401
```

`MAX_UPLOAD_BYTES`（32MB 上限）**挡不住**——那个检查在 `_read_upload_limited()` 里，
发生在 multipart 已经解析完之后。

### 同版本其他 CVE 的可达性

| CVE | 类型 | 本项目 |
|---|---|---|
| `GHSA-wp53-j4wj-2cfg` | 任意文件写入（CVSS 最高） | **不可达**：需非默认配置 `UPLOAD_DIR` + `UPLOAD_KEEP_FILENAME=True` |
| `GHSA-mj87-hwqh-73pj` | 大 preamble DoS | 不可达：被 boundary 校验快速拒绝 |
| `GHSA-5rvq-cxj2-64vf` | 分号二次时间 DoS | 部分：仅 `x-www-form-urlencoded`，本项目只用 multipart |
| `GHSA-v9pg-7xvm-68hf` | 负 Content-Length 缓冲 | 未验证：需真实 HTTP 层伪造非法头 |

升级到 `0.0.32` 一次性覆盖上述全部。

## 2. python-dotenv：1.2.1 → 1.2.4

`GHSA-mf9w-mj56-hr94`：`set_key()` 跟随符号链接导致任意文件覆盖。

**本项目不可达**——只用 `load_dotenv()` 读配置，从不写。

升级理由是成本极低（改 1 行），且消除审计报告噪音。

## 3. ortools：保持 9.11.4210（**不要升**）

`9.15.6755` 在 Python 3.12 调用 `CpSolver.Solve()` 会 **Segmentation fault**，
Python 层无法捕获、pytest 直接中断。

详见 `docs/ortools-compat.md`。

**审计工具会把 ortools 标为「落后」，这是已知且必要的锁定。**

### 一个必须注意的坑

首次审计时，我在自己环境测得「全部 1-3ms 拒绝」，差点结论「漏洞不可达」。

原因：**环境装的是 0.0.32（已修复），项目锁的是 0.0.20（有漏洞）**。

**依赖漏洞审计必须验证「测试环境 == 目标环境」。** 假阴性比假阳性更危险——它会让人不去修。
