### B. 重新引入学生课表链路（推翻 2026-10-23 边界）

- **内容**：恢复 4 个文件（588 行，git 可取）+ 3 端点 + agent/scheduler 构造参数
  回滚 + 冲突学生腿 + `impact-analysis` 的 `affected_students` + `RescheduleView`
  渲染；定「谁上传」（维持 require_admin 或放开给教师？）；前端接入形态；minor
  判定（同一学生同段两课——**前提：学生名单从哪来**，原 PDF 解析已随链路退役）；
  force 全链（云端表加列 → `approveCloudRequest` 传参 → AdminView 勾选 →
  `ApplyMoveRequest.force` → `_apply_reschedule` 放行 core → `applied_moves`
  记录 force 标记与决定人）
- **PII 暴露面**（项目判据＝匿名访客能否读到）：学生姓名/学号只要不进免鉴权读
  路径即可控；但课表结构数据（班级×时段×课程）经任何免鉴权端点输出即中风险，
  需逐端点重审；R-65 的硬边界测试（锁死"永远不管学生事务"的断言）须先删改——
  那些测试正是防回归的护栏，拆护栏需替换同等强度的新护栏
- **代价**：与 R-65 全部清理工作相反；重建前提（学生名单来源）本身不牢
- **工作量**：重构级，估 2-3 天（含测试重写与 PII 端点重审）

### C. 不碰学生数据，重定义「轻微」

- **内容**：轻微 = 「有低成本替代解的核心冲突」。唯一自然候选：**场地冲突且
  同时段存在其他空教室**（数据现成——`scan_table` 的 room 占用桶 + 空房查询）。
  这类标 `can_force=True`；`/apply-move` 加 force（审批人显式 override），
  `applied_moves` 记录；云端表加列 + AdminView 勾选（同 B 的 force 管线，
  但不碰任何学生数据）
- **优点**：零 PII、不推翻边界、工作量小（估 0.5-1 天）
- **缺点**：**语义偏离导师原话**——导师的「轻微」是个别学生维度，不是"有替代解"
  维度；且「force 永久不做」是架构文档明文，选项 C 本质是显式重新授权 force，
  需教秘确认这个重定义可接受（"有空教室我自己不会换？"——可能被认为没价值）
