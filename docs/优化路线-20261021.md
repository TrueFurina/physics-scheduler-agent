### 这一批踩到的真坑（值得记住）

**"我把视图做成懒加载了" ≠ "它真的不在首屏"**。第一次只改了 `React.lazy`，构建出来的
`vendor` 仍是 166.6 kB，且 `index.html` 依然 `preload` 它 —— 因为 `manualChunks` 把
**axios（首屏静态必需，`api/client.ts` 用它）和整条 markdown 解析链塞进了同一个 `vendor`**，
于是首屏为了 axios 把 markdown 也一起拖了下来，懒加载白做。

判定方法（别靠肉眼）：

```bash
grep -oE 'from"\./[A-Za-z0-9_-]+\.js"' webui/assets/index-*.js | sort -u   # 静态依赖
grep -oE '(src|href)="/assets/[^"]*"' webui/index.html                       # 预加载清单
```

修法：`manualChunks` 里给 axios 单独一块（`http`）。之后 `index.html` 预加载只剩
`index.js + react-vendor + http + css`，`vendor`（117.8 kB，纯 markdown 链）退出关键路径。

> 顺带修掉一个真缺陷：调课沙盘里 `['567','678','91011'].map(ts => (<>…</>))` 的外层
> Fragment **没有 key**（并行排课那边写了 `<Fragment key={ts}>`，这边漏了），React 会报
> key 警告。拆到 `RescheduleView` 时改成 `<Fragment key={ts}>`。

## 一·D、第四批：补上「懒加载引入的新崩溃面」——视图级错误边界（2026-10-21 16:20）

上一批为了首屏体积加了三个 `React.lazy`。**这是一次自己给自己制造风险的操作**：在 React 18 里，
渲染期任何抛错若无人接管，会把**整棵树**卸载 —— 用户看到纯白页面，连顶部导航一起消失。
而 `import()` 的 chunk 请求失败（网络抖动、部署切换瞬间、代理层 5xx、浏览器缓存被清）
正是渲染期抛错，`Suspense` 只接 pending、**不接 error**。

关键点：这不是"理论上可能"，而是"加懒加载就必然新增"的失败模式。原来全同步 import 时，
chunk 失败会表现为首屏 HTML 拿不到 JS（浏览器原生白屏，但那是**加载前**）；
现在页面已经跑起来了、用户点了一下按钮才去拉 chunk，失败了就整页消失 —— 用户体验上更糟，
因为他已经在系统里、可能刚填好调课表单。

### 做法

| 项 | 内容 |
|---|---|
| 组件 | `src/components/ErrorBoundary.tsx`（类组件，`getDerivedStateFromError`） |
| 挂载位置 | `<main>` 内容区整体包一层，**`key={view}`** ⇒ 切视图自动重置，不会"一次崩溃永久废墟" |
| 错误分流 | 识别 5 种浏览器的 chunk 失败措辞（Chrome / Safari / Firefox / webpack 系）⇒ 文案「页面资源已更新，需要重新加载」+ 按钮走 `location.reload()`；其余渲染异常 ⇒「这个模块遇到了问题」+ 重试 + 折叠的「技术详情」 |
| 为什么 chunk 错误不给「重试」 | 同一 URL 的模块记录已被标记失败，重挂载边界必然再失败；只有重拉 `index.html`（新哈希）才有救 |

### 反证（这是本项目要求的标准：先证明"病是真的"）

在**同一份产物**上，只删掉边界的两行 JSX 与 import，重新构建，然后用 Playwright
`route.abort()` 掐断 `ParallelView-*.js`，再点「并行排课」：

| 版本 | `#root` 子节点数 | 页面文本长度 | 顶部导航 | 提示卡 |
|---|---|---|---|---|
| 无边界（对照） | **0** | **0 字** | **消失** | 无 |
| 有边界 | 1 | 197 字 | **仍在** | 有 |

即：**没有边界就是教科书式白屏**（`rootChildren: 0`），且用户无法自救；
有边界时教秘能看见原因、能切到别的功能继续干活。

### 验证

| 项 | 结果 |
|---|---|
| `npm test` | **24 → 30 passed**（新增 `ErrorBoundary.test.tsx` 6 项：五种浏览器措辞全认、5 类普通错误不误判、无错时不影响正常渲染、异常时错误细节只进折叠区、重试能恢复、「chunk 场景不给重试」） |
| `pytest` | **123 passed**（未动后端） |
| `probe_ui_flow.cjs` | **8/8 → 9/9**（新增第 9 项「🛟 懒加载失败降级」：故意 abort 一个按需 chunk，断言提示卡出现**且**顶部导航仍可用） |
| `probe_demo_path.cjs` | **10/10**（登录三法 + 微信扫码不受影响） |

> 探针里这项刻意**单独开一个浏览器上下文**：它要制造失败请求，若混在主上下文会把
> 「全程失败请求＝0」这条基线永久染红，让人以后不再相信这条检查。
>
> 顺手修掉一个 `tsc` 拦下的问题：只 `throw` 的函数返回值被推断为 `void`，
> TS2786「不能作为 JSX 组件」。这类错误 `vitest`（esbuild 转译、不做类型检查）**不会报**，
> 只有 `npm run build` 里的 `tsc -b` 会 —— 所以**别只用 `npm test` 当"绿"的证据**。

## 一·E、第五批：把探针从"手工仪式"变成一条命令（2026-10-21 16:28）

之前每次跑 UI 探针都得手敲一长串：

```bash
# 旧做法：必须先进受管 workspace、必须设 NODE_PATH、必须写死 node 与浏览器路径
cd C:/Users/Lenovo/.workbuddy/binaries/node/workspace
NODE_PATH=".../node_modules" "<受管 node 绝对路径>" SITE=http://127.0.0.1:8020/ E:/Program/physics-scheduler-agent/scripts/probe_ui_flow.cjs
```

这不是"麻烦"，而是**探针进不了 CI 的真实原因**：依赖解析和浏览器路径都写死在别人机器上。
本轮把它拆掉。

| 改动 | 说明 |
|---|---|
| 新增 `scripts/_browser.cjs` | 共用装配：`playwright-core` 按候选列表兜底（项目依赖 → 受管 workspace → `PW_CORE_PATH`）；浏览器**自动发现**（`CHROME` → Playwright 缓存里修订号最大的 `chromium-*` → 系统 Chrome/Edge）；统一 `--no-proxy-server` |
| 去掉硬编码 `chromium-1243` | 原先浏览器一升级，两个探针同时报 "file not found"，看起来像代码坏了。现在取最新一份 |
| `playwright-core@1.64.1` 进 `devDependencies` | 版本**对齐**受管 workspace 里那份（它配的正是现有 Chromium），漂移会导致 CDP 不匹配 |
| npm 脚本 | `npm run probe` / `npm run probe:demo` / `npm run verify`（= `tsc -b && vitest run`） |

现在只需要：`cd frontend && SITE=http://127.0.0.1:8023/ npm run probe`

### 这轮被逼出来的两处"看似探针坏了"

1. **`require('./_browser')` 找不到** —— Node 的 CJS 解析只尝试 `.js/.json/.node`，**不含 `.cjs`**。
   必须写全 `require('./_browser.cjs')`。
2. **`probe:demo` 在本地跑 8/10，线上 10/10** —— 不是回归：云端会校验 OAuth callback 域名，
   `127.0.0.1` 不在白名单，`authorize` 直接 400、二维码拉不出来。
   ⚠️ 顺带纠正一个此前记录失真：之前"本地 10/10"其实是**打到了线上** ——
   该探针读的是 `PROBE_URL`，而当时传的是 `SITE`，环境变量名不同、被静默忽略。
   现已在本地地址时于汇总后打印说明，避免下一个人去白抓 bug。

### 探针改成三态（PASS / FAIL / SKIP）

线上旧产物是**单包**，根本没有 `ParallelView-*.js`，第 9 项「懒加载失败降级」掐不到 chunk。
第一次跑出来是 FAIL（`waitForFunction` 超时），这属于"误报"：会被读成"降级功能坏了"。
改成三态，并统计"跳过"项：

| 目标 | 结果 |
|---|---|
| 本地新产物（有按需 chunk + 边界） | **9/9 通过**（第 9 项：`chunk 中断 1 次，显示提示卡（有）且顶部导航仍可用（是=非白屏）`） |
| 线上旧产物（单包，无边界） | **8/8 通过（另有 1 项跳过）** —— 第 9 项明确标 SKIP 而非 PASS |

> 三态不是"宽容"，是**准确**：把测不到的东西记成 PASS 才是真的失职；记成 FAIL 则会训练人忽略红灯。

### 怎么发现的（顺序很重要）

1. 先量后端：8 个 GET 全部 2–14ms ⇒ **性能已经不是瓶颈**，继续优化是自欺。
2. 于是问"哪段代码没有被任何测试/探针覆盖"——答案是**产品主路径第 ③ 步（调课沙盘）**。
   `probe_ui_flow.cjs` 点完"我的课程"直接跳去了"并行排课"，把最核心的那一页跳过了。
3. 新写探针（`probe_reschedule_flow.cjs`）一跑，三个缺陷自己跳出来（见下）。
4. 顺带发现：`/impact-analysis` 返回 `affected_teachers: ["2024级应用化学1、2班"]` —— 班级名出现在教师栏。

### R-19 🔴 P0 · 一个慢请求把全站冻住 8 秒

| 项 | 内容 |
|---|---|

### R-28 🟠 P1 · 中文界面里直出 axios 英文原文（12 处 catch 站点）

| 场景 | 教秘看到的原文 |
|---|---|
| 首屏（`/teachers` 500） | `加载失败：Request failed with status code 500（可刷新页面重试）` |
| ② 我的课程 | `加载课程失败：Request failed with status code 500` |
| ⚡ 一键排课 | `并行排课失败：Request failed with status code 500` |
| 📊 统计面板 | `利用率与工作量统计加载失败：Request failed with status code 500` |
| 💬 自然语言调课 | `❌ 请求失败：Request failed with status code 500` |

**根因**：全站统一写法 `err.response?.data?.detail \|\| err.message`。
`detail` 只在**后端主动抛 `HTTPException`** 时才存在；而以下三种情况它会退化成 axios 原文：

- 未捕获异常 → FastAPI 回 `text/plain: Internal Server Error`（没有 JSON、没有 detail）
- 后端起不来 / 网络断 → `Network Error`
- 60s 超时 → `timeout of 60000ms exceeded`

而这三种正是公网沙箱上**最常见的**故障形态（进程被回收、冷启动慢）。越常见的故障，文案越不像人话。

**修复**：新增 `frontend/src/utils/apiError.ts` 的 `describeApiError()`，12 处 catch 全部改走它。
映射表按"教秘能做什么"组织，而不是按状态码堆砌：

| 输入 | 输出 |
|---|---|
| 后端给了中文 `detail` | 原样用；缺指引才补"（请稍后重试或刷新页面）"，不重复 |
| `detail` 是数组（422 校验） | `参数校验失败：field required；bad week` |
| 500 / 502（无 detail） | `服务端出错（HTTP 500），请稍后重试或刷新页面。` |
| 401 / 403 | `登录状态已失效或没有权限，请重新登录后再试。` |
| 404 | `接口不存在（404），服务端版本可能不一致，请刷新页面后重试。` |
| `ERR_NETWORK` | `无法连接服务（网络中断或服务未启动），请检查网络后刷新页面重试。` |
| `ECONNABORTED` / timeout | `请求超时（服务可能正忙），请稍后重试。` |

与 `cloud.ts` 的 `describeCloudError` **分工不复用**：那个处理云端 SDK 的错误码
（`gateway_` / `quota_` / `auth_`），这个处理自家 FastAPI 的 HTTP 状态，混用会把两类原因搅在一起。

回归锁：`frontend/src/utils/__tests__/apiError.test.ts`（11 项，其中一项把 7 种输入全跑一遍，
断言输出**不含** `Request failed with status code` / `Network Error` / `timeout of` 等英文原文）。

### 一·L 审批闭环：教秘点了"同意"，课表一个字节都没变（第十二批，2026-10-21 18:20）

前十一批全在验**读**：沙盘推荐得对不对、错误提示说不说人话、导出能不能打开。
产品还有一条**写**路径——教师提交申请 → 教秘审批 → 排课数据变更。
这条路上任何一环断了，界面都照样显示"操作成功"：写路径的失败不会让页面报错，
只会让课表悄悄没变，而**没人会再去查第二遍**。

#### 怎么找到的

不是靠读代码猜，是靠问一个产品问题："这条链最后一步是什么？"
`App.tsx:766` 的 `handleApprove` 只有两行有效动作：`approveCloudRequest(...)`
把云表 `status` 改成 `approved`，然后重新拉列表。**排课数据在这一步完全不参与。**

而 `_apply_reschedule`（能移记录、能检冲突、能写 `applied_moves` 供重启重放）
只挂在 `POST /requests/{id}/approve` 上 —— 前端对这个接口**一行调用都没有**。
两边通道不同：工单在云表（跨设备、跨会话），排课数据在服务端进程内存。

#### R-36 🔴 P0 审批通过后排课数据不落地

| 环节 | 修复前 | 修复后 |
|---|---|---|
| 教秘点"同意" | 云表 `status=approved`，到此为止 | 同上，接着调 `/apply-move` |
| 排课记录 | **不动** | 第3周 → 目标周，`applied=1` |
| 「我的课程」 | 周次仍是 `3-3周` | 变成 `2-3周` |
| 数据体检 / 沙盘 | 看不见这次调课 | 立即可见 |
| 重启后 | 调整丢失 | `applied_moves` 重放，调整仍在 |

**为什么不能简单地把两个请求合成一个**：前端写云表（浏览器直连云 SDK），
后端改内存（FastAPI）。合并等于让后端去信任前端传来的工单内容 —— 那就绕过了
云表的权限边界。所以拆成两步，第二步显式调用、显式报结果。

**修法**：

1. 新增 `POST /api/reschedule/apply-move`（挂 `require_admin`）：不碰任何工单表，
   只按调课内容移动排课记录，复用已有的 `_apply_reschedule`。
   语义上刻意与"工单"解耦——两边 id 体系不同（云表 id vs 本地 SQLite id），硬接会串号。
2. `applied_moves` 加 `idem_key` 列 + 应用前查重。审批台按钮**没有 `disabled`**
   （`AdminView.tsx:51`），双击/网络重试会打两次；幂等键让第二次直接返回
   "已于 xx 应用过"而不是再跑一遍匹配。⚠️ 不夸大：第二次跑大概率也会被冲突挡掉，
   这个键的真实收益是**不让 `applied_moves` 长出同源重复行**（重启重放时会重复执行）。
3. 前端 `handleApprove`：审批成功后立刻应用，并把结果原样贴出来 ——
   `✅ 已移动 N 条` / `⚠️ 已批准但目标周该时段已有安排，N 条未自动移动` /
   `⚠️ 审批已记录，但排课表未自动更新：<原因>（需人工调整）`。
   三种结局三种说法，"批了但没生效"绝不能被说成"审批成功"。
4. 驳回路径**不调用**应用接口（驳回只是标记，不该动课表），单测锁死。

## 一·M、第十三批：首屏第一个按钮给出的课表，没有"周次"这一列（2026-10-21 18:23）

#### 怎么找到的

## 一·X、第二十六批（R-58）：绪论类项目纳入主数据 —— 台账可见、但不排课

### 设计：区分「存在」与「可排」

| 维度 | 旧 | 新 |
|---|---|---|
| 项目实体 | 绪论/考试类**不建** | **一律登记**（台账可见、可指定课程、可导出台账） |
| 教师/场地/班级**实体**累积 | 跳过绪论 | **维持跳过** —— 实测若计入，17 个班的 `week_min` 统一提前 1 周（绪论在该班第一次实验之前），求解器周次窗口随之放宽，**那是 R-51 锁定的产品边界**（"时间由教务给定"），不该顺手改 |
| `schedulable` | 无此概念 | 项目名的**派生函数**（`is_schedulable_project`），**不可被用户覆盖** —— 否则把"考试"改成可排，求解器就会去排一场考试 |
| 求解器派生任务 | 天然安全（绪论根本不在主数据） | **必须显式过滤**：绪论项目进了主数据，教秘经 CRUD/台账导入给它加个班级，`_master_derived_tasks` 就会派生绪论待排任务被排掉 |

### 这一批揪出的三个真问题（都不是"功能没写"，是口径/参数错）

**① 长实验有两种表示，只检一种＝截短静默丢课**

真实表有 12 个单元同周同天地占多个时段：多数是**多行**（每行一个时段），
但有 6 个是**单行多节次**（`blocked=["567","678"]`，即 R-40 的 `14:00-17:00`）。
第一版 `long_sessions` 只按多行分组检测，漏了单行那种 ⇒ 落地会把第二时段
**静默砍掉**——方案每单元只排一个时段。修：两种表示都检测，预览单列
「落地后这些长实验将被截短，请在教务系统人工补回第二时段」。不改 CP-SAT 模型（回归风险）。

**② 时间戳秒级精度 ⇒ 同一秒内落地恒赢**

`applied_at` / `landed_at` 都是 `timespec="seconds"`。落地与调课落在同一秒时，
重放排序退化成 `kind` 字典序（`land` < `move`）——**恰好违反**「后发生者赢」的
设计目标：先发生的调课会被后发生的落地静默吞掉。两处都升到微秒精度。
重放顺序两个单测（落地后调课赢 / 调课后落地赢）因此是**真实排序**而非字典序兜底。

**③ `solve_all` 时限与它自己文档记录的证据错配**

代码 `flatten_seconds=3.0`（一阶段 5 秒），文档写着「60 个一片 **7 秒**可解」。
全量套件里真实表测试 **51/171** 失败；单独跑也 **0/3** 通过。二分 + pytest 纯净
上下文复现，证明与前置测试无关——是 CP-SAT 时间盒的固有不确定性（UNKNOWN），
**代码比它自己的证据还紧 2 秒**。改默认 `5.0` 后单跑 3/3、全量 349 绿。
教训：**代码参数必须与文档记录的性能证据一致，否则 CI 绿是运气**。

## 三、评估过但不建议做的（留档以免重排）

| 想法 | 结论 |
|---|---|
| 把排课数据放 Redis / 外部存储 | ❌ 沙箱单进程有状态，引入外部依赖换取"跨重启存活"不划算。R-18 已用"自愈 + 前端重试"解决可用性，成本低两个数量级 |
| 给数据接口加鉴权 | ❌ 教秘主路径（教师选择/沙盘/冲突/排课/体检/统计）必须免登录，加了直接废演示。治理手段是限流，不是门禁 |
| 加大 gzip 级别 / 换 brotli | ⚠️ 边际。已是 zlib level 9；brotli 需额外依赖且沙箱不保证支持，收益约再降 10–15KB，不值得引入构建复杂度 |
| 缩短 `parallel/solve` 的 CP-SAT 时限 | ❌ 24/24 是演示的核心结论，降时限换速度会牺牲"全排定"，本末倒置 |
| 前端全量重写为 Next.js/SSR | ❌ 单页内部工具、无 SEO 需求，改造收益为负 |

### R-67-C 探针 waitForFunction 签名 bug（本轮最大探针暗坑）

- 现象：`probe_ui_flow` 打本地时 auto-schedule（41s）/ solve-all（33s）两个场景
  "30s 超时"，而源码里写的是 120s/180s——**配置从未生效**
- 根因：Playwright `page.waitForFunction(fn, arg, options)` 签名——`{timeout: N}` 作为
  **第二参**被当成传给页面函数的 `arg`，options 缺失 ⇒ 全部按默认 30s 超时。实测验证：
  第二参传 `{timeout:1500}` 对 3.5s 后才出现的文本**不会**早退
- 波及面：4 个探针文件 32 处（ui_flow 10 / reschedule_flow 14 / faults 5 / newviews 3）；
  一直被掩盖是因为线上旧后端 2.7s 就返回、30s 默认够用；本地全表分片求解 40s 才爆
- 修法：统一 `null, { timeout }` 三参形式（newviews 的 `waitForText` 辅助函数本就是
  正确写法，以它为范本）；修后 ui_flow 本地 16/16（auto-schedule 40.2s＜120s 窗口）
- **次级发现**：solve-all 超时后**迟到的响应**会把大区块插到 CP-SAT 结果区上方，
  把结果顶出视口——探针的"结果区在视口内"断言级联失败。超时修好后级联消失
  （探针场景间有隐式时序依赖，写探针时序时要注意）
