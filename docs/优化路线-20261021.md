## 一、本轮已落地（5 项，全部实测）

| # | 优化 | 改动 | 实测效果 |
|---|---|---|---|
| 1 | **全站 gzip** | `main.py` 挂 `GZipMiddleware(minimum_size=1024)`；注册在 CORS **之前**（后注册者在外层，保证异常响应仍带 CORS 头） | JS 主包 `439,436 → 135,361 B`（**−69.2%**）；`parallel/overview` `13,917 → 1,587 B`（**−88.6%**）；`stats` `1,434 → 433 B`（−69.8%）。响应头新增 `vary: Accept-Encoding` |
| 2 | **哈希资源长缓存** | `_HashedAssetFiles(StaticFiles)` 给 `/assets/**` 加 `Cache-Control: public, max-age=31536000, immutable` | 二次访问**零网络往返**（原先虽无 `max-age`，浏览器每次仍要发条件请求换 304）。Vite 文件名带内容哈希，重发布即新 URL，无脏缓存风险 |
| 3 | **index.html 强制重校验** | SPA 兜底返回 `Cache-Control: no-cache`（ETag 仍在，多数请求以 304 结束） | 修掉一个**尚未发生但必炸**的场景：index.html 被启发式缓存 ⇒ 重发布后旧 index 指向已删除的旧哈希资源 ⇒ 白屏 |
| 4 | **`/health` 深度探活** | 返回 `{status, uptime_s, data:{loaded, total_entries}}`，**不触发加载**（保持廉价，可被高频轮询） | 原先恒 `{"status":"ok"}`，把 R-18 的真实成因（进程活着、内存清零）**完全掩盖**。现在外部监控能直接看出 `loaded:false` |
| 5 | **消除每次刷新的整表重解析** | `App.tsx` 首屏改为先 `GET /status`，`loaded=false` 才 `load-default` | 前端实测：一次页面加载对 `/load-default` 的调用 **1 → 0**（探针期间日志仅 1 次 POST，且是手工 curl），改为 1 次 `GET /status`。省下每次刷新 ~1.0s CPU（本地 0.98s / 冷沙箱 3.8s） |

附加：闭合 **D-7** —— `/load-default`（整表重解析）与 `/parallel/export`（落盘 xlsx）两个**免鉴权** POST 各挂 20/分钟·单客户端限流。

**验证**：`pytest backend/tests -q` → **111 passed**（106 → 111，新增 5 项：gzip / immutable / index no-cache / health 深度字段 / D-7 阈值）。
**回归**：本地 `probe_ui_flow.cjs` **7/7 通过**，首屏 425ms，一键排课 4931ms（24/24），0 JS 错误、0 失败请求。

> ⚠️ 以上 5 项**均待随 D-9 一起发布**才在线上生效。发布授权不跨轮次，需在最新一条消息里出现"发布/上线/部署"。

## 一·B、第二批已落地（P1 三项 + P3 三项，2026-10-21 16:05）

| # | 优化 | 做法 | 实测 |
|---|---|---|---|
| 6 | **代码分割 + 云 SDK 懒加载** | `vite.config.ts` 加 `manualChunks`（`react-vendor` / `cloud-sdk` / `vendor`）；`cloud.ts` 的 `getCloud()` 改动态 `import()`（共享 Promise 防并发重复初始化、失败可重试）；首屏会话恢复推到 `whenIdle()` | 首屏 JS **3 个 chunk 共 360KB**（原 439KB 单块）；gzip 首屏 **115KB**（原 135KB）。`cloud-sdk` 70KB **不在首屏**：浏览器实测首屏 215ms 才出现标题，SDK 在 **797ms** 由空闲回调拉起。**重发布时 app chunk 仅 15KB(gz)，其余走 immutable 缓存** |
| 7 | **CP-SAT 预热** | `app/engine/warmup.py` + `main.py` lifespan 起 daemon 线程跑两变量小模型；状态写入 `/health.solver` | A/B 同机实测：**首次 `/parallel/solve` 2.05s → 0.89s（−56%）**。预热本身 448–459ms，`/health.solver.status=ok` 可核对 |
| 8 | **Excel 解析缓存** | `app/utils/parse_cache.py`：以 **(绝对路径, mtime_ns, size, 版本)** 为签名，命中即跳过 openpyxl；顺带把 `roles` / `semester_start` 在**同一次打开**里算完（原先 `/teachers` 为读 13 条备注要重开整个工作簿） | `/load-default`：冷解析 0.34s → **缓存命中 0.025s**（13.6×）；`/teachers`：0.28s → **0.0027s**（100×）。**fail-closed**：JSON 损坏 / 版本不符 / 行结构异常 / mtime 变化 → 一律重解析（7 项测试锁定，含"缓存坏了仍是同样的数据"） |
| 9 | **前端单元测试** | 引入 `vitest@2`（vite5 兼容版），`npm test`；抽出 `src/utils/async.ts` 使 `withRetry` / `whenIdle` 可测 | **9 项通过**。**并借此抓到一个真 bug**：`describeCloudError` 里 `gateway_stream_interrupted` 的精确匹配写在 `startsWith('gateway_')` **之后**，该分支永远不可达 —— 用户会看到"模型服务暂时不可用"，而真相是流中断、内容其实还在。已调整为精确匹配优先 |
| 10 | **死依赖清理** | 移除 `react-router-dom`（`App.tsx` 0 处 `Routes`/`useNavigate`，`main.tsx` 里只挂了个不注册路由的 `BrowserRouter`）与 `lucide-react`（0 引用） | `vendor` chunk 172.3KB → 166.6KB；少两个依赖的安装体积 |
| 11 | **结构化可观测性** | 纯 ASGI 中间件 `_ObserveMiddleware`（**刻意不用** `@app.middleware("http")`，避免 BaseHTTPMiddleware 缓冲静态文件流）：每个响应带 `x-response-time-ms`，只对 **≥400 或 ≥1000ms** 打 JSON 日志；`/health.http` 暴露 `requests/errors/slow/throttled` | 实测 `<health>` 返回 `{"requests":N,"errors":0,"slow":0,"throttled":0}`；405 请求后 `errors` 正常 +1 |

**验证**：`pytest backend/tests -q` → **123 passed**（111 → 123）；`npm test` → **9 passed**；
本地 `probe_ui_flow.cjs` **7/7**（首屏 **198ms**、一键排课 **1859ms**、0 JS 错误、0 失败请求）；
`probe_demo_path.cjs` **10/10**（登录三法 + 微信扫码链路仍通）。
**附带收益**：pytest 整套耗时 **56s → 10s**（解析缓存让每个用例不再重解析 xlsx）。

> `probe_demo_path.cjs` 会打印 6 条 `ERR_CONNECTION_REFUSED` 的 console 错误 —— 这是**既有噪音**：
> 对**线上旧版本**跑同一探针同样出现 6 条，与本次改动无关（本机无代理环境下微信二维码页的外链）。

**唯一未做项**：`App.tsx`（1712 行）按视图拆分。理由 —— 收益是纯可维护性，而风险集中在十几个
互相纠缠的 state 与 handler 上，当前只有端到端探针兜底、没有组件级测试；正确做法是按视图
逐个拆、每拆一个跑一次探针，属独立一轮工作，不适合和其它改动混在一次提交里。

## 三、评估过但不建议做的（留档以免重排）

| 想法 | 结论 |
|---|---|
| 把排课数据放 Redis / 外部存储 | ❌ 沙箱单进程有状态，引入外部依赖换取"跨重启存活"不划算。R-18 已用"自愈 + 前端重试"解决可用性，成本低两个数量级 |
| 给数据接口加鉴权 | ❌ 教秘主路径（教师选择/沙盘/冲突/排课/体检/统计）必须免登录，加了直接废演示。治理手段是限流，不是门禁 |
| 加大 gzip 级别 / 换 brotli | ⚠️ 边际。已是 zlib level 9；brotli 需额外依赖且沙箱不保证支持，收益约再降 10–15KB，不值得引入构建复杂度 |
| 缩短 `parallel/solve` 的 CP-SAT 时限 | ❌ 24/24 是演示的核心结论，降时限换速度会牺牲"全排定"，本末倒置 |
| 前端全量重写为 Next.js/SSR | ❌ 单页内部工具、无 SEO 需求，改造收益为负 |
