## 一、本轮已落地（5 项，全部实测）

| # | 优化 | 改动 | 实测效果 |
|---|---|---|---|
| 1 | **全站 gzip** | `main.py` 挂 `GZipMiddleware(minimum_size=1024)`；注册在 CORS **之前**（后注册者在外层，保证异常响应仍带 CORS 头） | JS 主包 `439,436 → 135,361 B`（**−69.2%**）；`parallel/overview` `13,917 → 1,587 B`（**−88.6%**）；`stats` `1,434 → 433 B`（−69.8%）。响应头新增 `vary: Accept-Encoding` |
| 2 | **哈希资源长缓存** | `_HashedAssetFiles(StaticFiles)` 给 `/assets/**` 加 `Cache-Control: public, max-age=31536000, immutable` | 二次访问**零网络往返**（原先虽无 `max-age`，浏览器每次仍要发条件请求换 304）。Vite 文件名带内容哈希，重发布即新 URL，无脏缓存风险 |
| 3 | **index.html 强制重校验** | SPA 兜底返回 `Cache-Control: no-cache`（ETag 仍在，多数请求以 304 结束） | 修掉一个**尚未发生但必炸**的场景：index.html 被启发式缓存 ⇒ 重发布后旧 index 指向已删除的旧哈希资源 ⇒ 白屏 |
| 4 | **`/health` 深度探活** | 返回 `{status, uptime_s, data:{loaded, total_entries}}`，**不触发加载**（保持廉价，可被高频轮询） | 原先恒 `{"status":"ok"}`，把 R-18 的真实成因（进程活着、内存清零）**完全掩盖**。现在外部监控能直接看出 `loaded:false` |
| 5 | **消除每次刷新的整表重解析** | `App.tsx` 首屏改为先 `GET /status`，`loaded=false` 才 `load-default` | 前端实测：一次页面加载对 `/load-default` 的调用 **1 → 0**（探针期间日志仅 1 次 POST，且是手工 curl），改为 1 次 `GET /status`。省下每次刷新 ~1.0s CPU（本地 0.98s / 冷沙箱 3.8s） |

附加：闭合 **D-7** —— `/load-default`（整表重解析）与 `/parallel/export`（落盘 xlsx）两个**免鉴权** POST 各挂 20/分钟·单客户端限流。

**验证**：`pytest backend/tests -q` → **111 passed**（106 → 111，新增 5 项：gzip / immutable / index no-cache / health 深度字段 / D-7 阈值）。
**回归**：本地 `probe_ui_flow.cjs` **7/7 通过**，首屏 425ms，一键排课 4931ms（24/24），0 JS 错误、0 失败请求。

## 二、候选优化（按性价比排序）

### P0 · 只有你能做的

| 项 | 内容 | 依据 |
|---|---|---|
| **D-9 发布** | 把 R-18 修复 + 本轮的传输/探活优化推上线 | 线上仍在跑 `index-CBVV35EQ.js`，用户仍可能再遇一次「加载课程总览失败」；修复只在仓库里 |
| **D-4 换口令** | `.env` 改 `ADMIN_PASS` 后重发布 | 默认 `admin/admin123`；不影响演示（真实审批走云 RLS） |

### P1 · 收益明确、风险低

| 项 | 内容 | 预期收益 | 风险 |
|---|---|---|---|
| **首屏代码分割** | `vite.config.ts` 加 `manualChunks`：`react-vendor` / `markdown` / `cloud-sdk` 三桶 + 云端 SDK 改 `import()` 懒加载 | 首屏 JS 从 435KB 单块下降到 ~200–250KB（gzip 135→~80KB）；**重发布时 vendor 命中 immutable 缓存**，用户只需重下 app 块 | 中低。需重跑构建 + 探针；懒加载 SDK 要注意登录态初始化时机 |
| **求解预热** | 启动后后台线程空跑一次 CP-SAT（或提前 import `ortools`） | 本地首次求解 5157ms → 稳态 ~1.5–2s（线上 1488ms）。**首次点击"一键排课"的等待差 3s+**，演示第一印象 | 低。预热失败必须静默吞掉，不能影响启动 |
| **解析结果落盘缓存** | `/load-default` 把 433 行解析结果序列化到 `backend/app/data/`，按 xlsx `mtime+size` 校验 | 冷启动 3.8s → ~0.2s；沙箱回收后的自愈几乎无感 | 中。**缓存失效判定错 = 静默返回旧数据**（比慢更糟），必须 fail-closed：校验不过就重解析 |

### P2 · 结构性改善（不改变外部行为）

| 项 | 内容 | 为什么值得做 |
|---|---|---|
| **`App.tsx` 拆分** | 1712 行单文件，5 个视图全在一个组件里。拆成 `views/` + `hooks/useScheduleData.ts` | 现在任何一处改动都要在 1700 行里定位；也是上面"代码分割"的前置条件（视图级懒加载需要视图是独立模块） |
| **前端测试** | 目前 **0** 个前端单测，全靠 2 个 Playwright 探针 | 探针验证的是"链路通"，锁不住"某个交互逻辑"。至少给 `withRetry`、错误文案映射、视图切换加 vitest |
| **D-8 演示数据** | 审批台当前 0 工单；唯一管理员＝唯一申请人 | 现场需两个账号（A 提交、你审批），否则"审批闭环"只能口述 |

### P3 · 卫生项

| 项 | 内容 | 依据 |
|---|---|---|

## 三、评估过但不建议做的（留档以免重排）

| 想法 | 结论 |
|---|---|
| 把排课数据放 Redis / 外部存储 | ❌ 沙箱单进程有状态，引入外部依赖换取"跨重启存活"不划算。R-18 已用"自愈 + 前端重试"解决可用性，成本低两个数量级 |
| 给数据接口加鉴权 | ❌ 教秘主路径（教师选择/沙盘/冲突/排课/体检/统计）必须免登录，加了直接废演示。治理手段是限流，不是门禁 |
| 加大 gzip 级别 / 换 brotli | ⚠️ 边际。已是 zlib level 9；brotli 需额外依赖且沙箱不保证支持，收益约再降 10–15KB，不值得引入构建复杂度 |
| 缩短 `parallel/solve` 的 CP-SAT 时限 | ❌ 24/24 是演示的核心结论，降时限换速度会牺牲"全排定"，本末倒置 |
| 前端全量重写为 Next.js/SSR | ❌ 单页内部工具、无 SEO 需求，改造收益为负 |
