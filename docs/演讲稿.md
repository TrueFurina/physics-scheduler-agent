## 第一部分：项目背景与竞品分析（约 1 分钟）

### 1.1 项目背景

**物理实验教学排课的真实痛点：**

- 物理实验涉及多专业、多教师、多实验室的复杂排课约束
- 教务系统管不了实验排课——论文验证："由于各种原因，很少有分组实验课出现在排课系统中，实验排课不得不停留在传统的人工模式"
- 教师临时调课会引发**多班、多教室、多实验室的连锁冲突**，人工协调效率低

**✅ 真实用户访谈验证（2026-10-08，物理实验教学负责人）：**

> "每半年都要提前向教学秘书索要每个老师手上带实验课程的课……注意时间、地点、班级冲突，还有老师上课也同步。"
> ——**印证了我们的三重冲突筛选（教室/学生/教师）符合真实工作流**

> "他要每一个实验项目进去以后……先把实验项目调出来，才可以排课。**所以你要注意，现在我们的痛点就在这里，重复性太大了。**"
> ——**指出教务系统逐项目排课的重复劳动，这正是我们"并行排课"要解决的**

> "把所有实验项目出来，分组分完以后，我把这个时间地点、安排的老师都进去，**就像 AI 一键全部完成。**"
> ——**理想形态，与我们的 CP-SAT 一键排课完全呼应**

**我们的切入点**：不是替代学校排课，而是为排课管理者和教师提供"调课辅助 + 冲突规避 + 并行排课"的智能体工具。

### 1.2 竞品分析（GitHub 全站深度调研）

**调研方法**：对 GitHub 全站高校排课/课表类项目进行检索，按星标与相关性筛选，逐一分析其技术方案与产品定位。

**同类项目技术架构（GitHub 检索结果）：**

| 项目 | 星标 | 核心方案 | 对我们的启示 |
|------|------|---------|-------------|
| mohadesehAtaollahi/university_scheduler | 1 | Django + OR-Tools(CP-SAT) 约束求解 + LLM 辅助（in progress） | **最接近我们**：约束求解 + LLM 增强是共识路线 |
| Fanhua041027/Smart-University-Course-Scheduling | 5 | 高校排课系统（传统 CRUD 管理后台） | 无 AI，纯管理后台，我们加了 AI 对话 |
| anteKpiechnik/course-scheduler | 4 | PHP 排课系统改造 | 传统技术栈，无冲突解释能力 |
| tiomanalu/Dynamic-University-Course-Scheduling | 1 | 多目标元启发式 + LLM | 学术算法路线，落地性弱 |
| anubhavJhanwar/Time-Table-Scheduler | 1 | AI 课表生成 | 面向课表生成，非调课场景 |
| Abdullahjaved15/AI-based-University-Timetable-Scheduler | 1 | AI 排课 | 同上，聚焦生成而非日常调课 |

**核心结论（3 条）：**

**① 排课求解的主流技术是 OR-Tools（CP-SAT）约束求解，不是贪心**
- 调研的 AI 排课项目几乎都用 `or-tools` 的 CP-SAT 求解器
- 我们当前的 auto_scheduler 是贪心算法（逐个放置，冲突数 0 但非最优）——这是"排课显得拉跨"的技术根因
- **改进方向**：换 CP-SAT 求解器，能处理 433 条真实数据的复杂约束（教室/教师/学生/轮次）

**② "AI + 排课"普遍处于"规划中"状态**
- university_scheduler 的 LLM-assisted 也是 "in progress"
- 说明**用 AI 直接排课还不成熟**，业界共识是：**约束求解做硬约束，LLM 做交互/解释/候选推荐**
- 这恰恰是我们已经做的架构（规则引擎兜底 + LLM 增强）——**方向是对的，被业界验证**

**③ 几乎没有项目做"调课"和"排课人视角"**
- 调研项目全是"排课生成器"（输入约束 → 输出课表）
- **没人做"排课管理员日常调课/冲突评估"**——这是我们的差异化！
- 我们聚焦的不是生成课表，而是**调课场景的冲突规避**——这正是真实痛点（论文佐证）

**我们的差异化定位：**

| 维度 | 竞品（排课生成器） | 我们（调课智能体） |
|------|-------------------|-------------------|
| 核心场景 | 学期初一次生成课表 | 日常调课冲突规避 |
| 目标用户 | 排课系统开发者 | 排课管理员、实验教师 |
| AI 价值 | LLM 辅助生成（多数未落地） | 大白话调课解析 + 候选推荐 + 咨询（已落地） |
| 冲突处理 | 输出课表 | 冲突原因透传 + 影响分析（市场空白） |

## 第二部分：效果展示、核心亮点与项目价值（约 1.5 分钟）

### 2.1 效果展示（四大模块一键演示）

**演示路径（建议现场操作）：**

```
① 身份选择 → 点"吴琳"卡片（系统知道用户是谁）
② 我的课程 → 看全部课程（可调/不可调标注）
③ 模板调课 → 选课程 + 目标周次 → 冲突筛选
④ 调课结果 → 可用时段（按星期分组+具体日期）+ 被排除时段（附原因）+ AI候选方案
⑤ 提交申请 → 管理员登录 → 审批同意/驳回
⑥ 选课咨询 / 实验辅导 → AI 问答（带实验知识源）
```

**演示讲解话术（边点边说）：**

> "① 教师选择身份——系统自动加载学校实验安排表，展示全部教师。这是评审强调的'系统应该知道用户是谁'。"
> "② 进入吴琳的工作台，看到她名下全部课程，标注可调/不可调。"
> "③ 选一门课、选目标周次，系统做三重冲突检查：教室占用、学生课表、教师时间。"
> "④ 看结果——可用时段按星期分组，还带具体日期（比如第7周的周一就是4月7日）；被排除的时段都标了原因，比如'教室被应用化学班占用'，这就是信息透传。系统还给了 AI 候选方案。"
> "⑤ 提交申请后，管理员登录审批（演示账号 admin/admin123），同意或驳回，全程有记录、重启不丢。"
> "⑥ 最后是选课咨询和实验辅导——基于 DeepSeek 大模型，结合实验知识源回答问题。"

### 2.2 核心亮点（6 个，详细）

| # | 亮点 | 说明 | 演示佐证 |
|---|------|------|---------|
| 1 | **三重冲突筛选** | 教室占用 / 学生课表（多学生并集）/ 教师时间，确保推荐时段无硬冲突 | 调课结果页绿/灰分列 |
| 2 | **原因透传** | 每个被排除时段都标注原因（"教室被XX班占用""学生该时段有课"）——评审强调的信息透传 | 灰色列表逐条附原因 |
| 3 | **火车票改签式交互** | 先看"我有哪些课"，再选"可改签时间"（王铮导师建议） | 我的课程 → 选课 → 看时段 |
| 4 | **AI 增强体验** | DeepSeek 大白话调课意图解析、AI 候选方案推荐、多轮追问补全信息 | 自然语言输入"我是吴琳，第六周的课调到下周" |
| 5 | **具体日期透出** | 周次→日期映射，可用时段显示"周一 04月07日"而非模糊的"周一" | 调课结果日期列 |
| 6 | **SQLite 持久化 + 13 个单测** | 申请单重启不丢，核心逻辑有测试保障 | 审批记录重启后仍在 |

### 2.3 项目价值（三个视角）

**对教师（使用者的价值）：**
- 调课从"问学委 + 人工查表"变成"一键筛出无冲突时段"
- 不知道"周一是哪天"？系统直接给具体日期
- 大白话也能调课，不用学系统操作

**对管理员（决策者的价值）：**
- 减少多班多教室冲突协调成本
- 每个申请都有审批记录、可追溯（SQLite 持久化）
- 冲突原因明确，驳回时有据可依

**对学校（采购者的价值）：**
- 数据驱动：各校上传自己的实验安排表即可部署（可推广）
- 本地化部署支持，满足校内部署要求
- 四大模块完整闭环，不是演示玩具

## 第三部分：核心设计与功能（约 2.5 分钟，重点）

### 3.1 系统架构

```
┌────────────────────────────────────────────────────┐
│       前端 React（四大模块导航 + 交互界面）         │
└────────────────────┬───────────────────────────────┘
                     │ HTTP/JSON
┌────────────────────▼───────────────────────────────┐
│           FastAPI 后端（/api/reschedule/*）         │
│  ┌──────────────────────────────────────────────┐  │
│  │       调课智能体 RescheduleAgent              │  │
│  │  规则解析 → LLM降级 → 三重冲突筛选 → 原因标注  │  │
│  └────────────────────┬─────────────────────────┘  │
│  ┌────────────────────▼─────────────────────────┐  │
│  │   LLM 解析器（DeepSeek，OpenAI兼容）         │  │
│  │   意图解析 / 候选方案 / 选课辅导咨询          │  │
│  └────────────────────┬─────────────────────────┘  │
│  ┌────────────────────▼─────────────────────────┐  │
│  │   数据层：实验安排表(433条) + 学生课表(3人)   │  │
│  │   + 调课申请单(SQLite持久化)                 │  │
│  └──────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────┘
```

**核心设计原则**：
1. **规则引擎保证正确，LLM 增强体验**——核心流程不依赖 LLM 稳定性
2. **系统知道用户是谁**——身份选择后展示名下课程
3. **信息透传**——每个被排除时段都有原因

### 3.2 四大核心模块

#### 模块一：排课（约束筛选 + 辅助生成）

- **三重冲突筛选**：教室占用（实验安排表）/ 学生课表（多学生并集）/ 教师自身时间
- **时间归一化**：解决 Excel 12 种时间格式导致的比对失效隐藏 bug
- **AI 候选方案**：从几十个可用时段中推荐 2-3 个最优并附理由
- 定位：辅助初稿生成，以学校已排定安排表（433条）为准

#### 模块二：调课（核心闭环）

```
身份选择 → 我的课程（可调/不可调）
  → 模板表单（选课程 + 目标周次）
  → 冲突筛选 → 结果（可用+被排除原因+AI候选）
  → 提交申请 → 管理员审批（SQLite持久化）→ 反馈
```

**双入口解析**：
- 模板表单：下拉选择，零输入负担（火车票改签式）
- 自然语言："我是吴琳，第六周的课上不了，调到下周" → LLM 意图解析
- 多轮追问：信息缺失时系统主动补全

#### 模块三：选课咨询（AI）

- 公共必修课强制必选（基于真实场景验证的需求判断）
- LLM 结合学生课表 + 实验知识源回答先修/学分问题
- 回答带结论 + 可操作建议

#### 模块四：实验辅导（AI）

- 覆盖实验原理、数据处理、误差分析、报告规范
- 回答基于实验知识源（实验名/教室/教师），后续可升级 RAG

#### 模块五：并行排课（访谈驱动的差异化功能）⚡

> 来源：2026-10-08 真实访谈——"所有实验项目列出来，分组分完以后……**就像 AI 一键全部完成**"

```
选课程 → 全部实验项目×学生组别一次列出
  → CP-SAT 一键求解：每个(项目×组) → (周次/时段/场地)
  → 约束保证：每组每周一个实验 + 场地互斥 + 教师互斥
  → 输出完整排课方案表（OPTIMAL，如 24/24 单元）
```

- 解决教务系统"逐项目重复排课"的核心痛点（访谈原话："重复性太大了"）
- 数据直接复用现有安排表的 项目/组别 字段，零新增数据收集
- 与 GitHub 调研结论呼应：约束求解做硬约束，正是业界主流路线

### 3.3 关键功能细节

| 功能 | 实现 | 亮点 |
|------|------|------|
| 可用时段显示 | 按星期分组 + 具体日期（周次→日期映射） | 用户知道"周一是哪天的周一" |
| 原因标注 | 每个被排除时段附原因类型+详情 | 评审核心要求的信息透传 |
| 时间友好显示 | 567 → 13:30-15:45 | 降低理解成本 |
| 管理员登录 | 审批台需账号验证，普通用户免登录 | 权限边界清晰 |
| Markdown 渲染 | 选课/辅导回答格式化显示 | 提升可读性 |

### 3.4 技术难点与解决

1. **时间格式统一**：Excel 12 种写法 → 归一化为节次标记（隐藏 bug，单测保障）
2. **约束求解 NP-hard**：贪心 + 局部约束控制规模，冲突数 0 为最优
3. **LLM 服务不稳定**：规则引擎兜底 + 超时优化（30s→60s）+ 静默降级
4. **多学生课表**：并集冲突检查，覆盖老师教多班场景

## 第五部分：项目心得、成长与后续规划（约 2.5 分钟，重点）

### 5.1 项目心得（3 条最有价值的认知）

**① "没需求" vs "需求方不是我"**
> 我一度质疑"这个项目根本没必要做"。最终明白：学生视角没需求（强制必修不需要选课），但排课管理者视角有需求（论文证明实验排课靠人工协调）。**"我没看到需求"不等于"没有需求"，可能是需求方不是我。**

**② 做减法与业务闭环不矛盾**
> 砍掉的是伪需求（签到、报告、选课系统），保留的是业务闭环完整性（四大模块都能演示）。**两者都对。**

**③ 写代码可以快，判断要慢半拍**
> 项目最大的教训是开头：没验证需求就写了一批 CRUD 排课系统，全部废弃。**产品经理第一反应应该是"验证需求"而不是"写代码"。**

**④ 真用户一句话，胜过十页竞品分析**
> 项目中期我们访问了物理实验教学负责人，他说"所有实验项目列出来……就像 AI 一键全部完成"——这句话直接催生了"并行排课"模块（CP-SAT 一键排定 24 个教学单元）。**走出去问真用户，比坐在电脑前调研更能找到真需求。**
