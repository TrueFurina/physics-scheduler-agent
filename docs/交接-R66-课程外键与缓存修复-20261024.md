## 2. 设计决策（已定，照此实现，勿反复）

### 2.1 显式课程外键
- `ScheduleEntry` 新增 `course: str = ""`（**构造参数末尾**，带默认值 ⇒ 对所有现有 8/10 位置参数构造点向后兼容）。
- 课程来源优先级（`course_bridge.resolve_course`）：
  1. **条目自带 `course`**（源安排表有课程列时解析而来）——权威、无歧义；
  2. 否则按项目名查主数据 `experiment.course` 反推；
  3. 都查不到回落 `DEFAULT_COURSE`（"大学物理实验"）。
- **为什么不在解析时用主数据物化 course**：主数据可被 CRUD 改，物化会陈旧。只有"源表自带"的课程才配当条目的显式属性。
- **不做**更激进的"experiments 按 (课程,项目) 重新键控"——高风险、收益仅理论性，过度工程。

### 2.2 课程列探测（关键教训）
- `_detect_course_col(sheet)`：扫安排表前两行表头，找课程列索引。
- **必须精确匹配别名**（`_norm_header(c) in MASTER_FIELDS["course"]`），**不能模糊子串匹配**。
- 原因：真实表第 8 列叫 **「课程类别」**（值 C/B/普物3），模糊匹配 `课程 in 课程类别` 会误命中 ⇒ 433 条全落密码值、`distinct_courses` 从 1 变 3、导出课程列显示"C"。**我已把模糊匹配改成精确匹配**（这是当前代码状态）。

### 2.3 「课程类别」是一个待用户拍板的产品发现（重要！）
真实安排表**确实有**一列课程区分信息，系统一直忽略（解析器只读 0–7 列）：

| 课程类别 | 行数 | 项目数 | 班级数 |
|---|---|---|---|
| C | 300 | 8 | 12 |
| B | 103 | 10 | 4 |
| 普物3 | 31 | 16 | 1 |

- **同一项目"扭摆法测物体转动惯量"同时出现在 C 和 B 下** ⇒ 这正是 P0-3 说的"同名项目跨两门课"歧义的**真实样本**。
- 每个班只属于一个类别（12+4+1=17 班）⇒ 若采用它，`distinct_courses` 1→3，但**跨课程撞车仍 0 处**（同班同类别，不会同格不同课）。
- **但**：C/B/普物3 是**分类码不是课程名**，直接进导出会让教秘看到密码；且改变 R-57/R-58 锁定基线（`test_real_table_baseline` 断言 `distinct_courses==1`）。
- **决策选项**（交给用户，别擅自决定）：
  - A) 不采用（当前实现）：精确匹配只认"课程/课程名称/课程名/所属课程"，「课程类别」不触发 ⇒ 基线不变，显式外键基础设施就绪，等有真·课程列的表才生效。
  - B) 采用「课程类别」为课程：需加 **码→名映射**（C→大学物理实验C 等），并改 `test_real_table_baseline` 基线为 3，导出显示映射后的名。
  - C) 把「课程类别」当**独立维度**（category），与 course 分开建模。
- **当前代码 = 选项 A**（向后兼容、基线不变）。若用户要 B/C，是另一批工作。

## 4. parse_cache 磁盘缓存 bug（已实测坐实 + 已修）

### 病
- `entries_to_rows` 自 v3 起产出 **10 字段**行（加了 time_raw/blocked），但 `_validate` 仍按 **8 字段**校验（`len(row) != 8`）。
- 后果：磁盘缓存**恒被判结构异常 ⇒ 永远 MISS ⇒ 每次冷启动重解析整张 433 行表**。进程内 `_MEMO` 绕过 `_validate`，故同进程内仍快、不易察觉。
- 优化路线里"冷启动 0.025s / 13.6×"是 **memo 的数字，不是真冷启动**。

### 实测证据（接手可复现）
```python
# backend/ 下，PARSE_CACHE_DIR 指向临时目录
db = ScheduleDatabase(); db.load_from_excel(path)   # 写缓存
# 读缓存文件：row 长度 = 10，_validate 期望 8
parse_cache._validate(real_payload, real_sig)  # -> False
parse_cache.reset_memo(); parse_cache.load(path)  # -> None（MISS）
```
实测输出：`cache row length: 10 (validate wants ==8)` / `_validate -> False` / `disk load after reset_memo: MISS`。

### 假绿（R-25 同族）
- `test_second_load_uses_cache_and_matches` 在 reset_memo 后即使磁盘 MISS，也靠 fail-closed **重解析**得到相同快照而变绿——它验"结果对"，从没验"缓存真被用上"。
- `test_cache_contains_roles_and_semester` 能过是因为它**没 reset_memo**，走的是进程内 memo。

### 修
- `_validate` 改用 `ENTRY_ROW_WIDTH`（=11，含 course）；序列化与校验共用同一常量，杜绝再漂移。
- 新增 `test_disk_cache_actually_hits_after_reset_memo`：缺陷版上必红（已满足 R-25"新判据先在缺陷版跑红"铁律——**接手请补做这步反证**：临时把 `_validate` 改回 `!= 8`，确认该用例红，再改回）。

3. 但 pytest 里却"解析缓存命中"且带 course 值。

### 最强假设（接手先验这个）
**陈旧 v5 缓存被命中**：我在**模糊探测**那次跑 pytest 时，`test_real_table_baseline` 用模糊代码解析 schedule.xlsx，把 course=C/B/普物3 写进了 **v5 磁盘缓存**。之后我收紧探测，但 **CACHE_VERSION 仍是 5**（收紧探测没再 bump），schedule.xlsx 的 mtime/size 也没变 ⇒ 那份陈旧 v5 缓存签名**仍判有效**、被命中。我 `host_safe_delete` 删的 `schedule-77a602bf81cb.json` **可能不是 schedule.xlsx 的那份**（或是 demo 表的），所以没清干净。

> 根因教训（写进项目方法论）：**改了解析逻辑但没 bump CACHE_VERSION ⇒ 旧缓存静默复活**。这正是 parse_cache.py 注释里"解析逻辑变更时 +1"规则要防的事，我自己踩了。
